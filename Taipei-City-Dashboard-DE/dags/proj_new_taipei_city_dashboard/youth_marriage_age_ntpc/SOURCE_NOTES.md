# 新北市結婚與離婚人數（按年齡組）

## 來源驗證

```
https://www.ris.gov.tw/rs-opendata/api/v1/datastore/ODRP069/{民國年度}?PAGE={n}&COUNTY=新北市
https://www.ris.gov.tw/rs-opendata/api/v1/datastore/ODRP071/{民國年度}?PAGE={n}&COUNTY=新北市
```

- 平台：內政部戶政司 RIS OpenData，免驗證；官方 API 文件：
  `https://www.ris.gov.tw/rs-opendata/api/Main/docs/v1`
- ODRP069「按發生的結婚」實測民國109–114皆有資料，即西元2020–2025。
- ODRP071「按發生的離婚／終止結婚」實測民國111–114皆有資料，即西元2022–2025；民國109、110查無資料。
- `COUNTY=新北市` 後每個有資料的年度為25頁、每頁最多2000列；114年度兩者各有48,720列。API的 `totalDataSize` 仍會顯示全國的618,240，不以它作新北筆數判定。
- 114年度實測計數合計：結婚 `36,498`、離婚／終止結婚 `18,026`。這裡的欄位說明是「人數」，不是居住人口分母；資料按性別與年齡組的事件／參與者人數保留。

轉換後共約 **41,000 列**：ODRP069 六年、ODRP071 四年。每個資料集／年度的完整交叉表是 48,720 個組合，但其中約 90.5% 為零值，已在對帳通過後濾除（見下方「表大小」一節）。

## 為什麼合併成一支 DAG

ODRP069與ODRP071的切面完全相同：行政區、婚姻類型、性別、原屬國籍、教育程度及年齡組。差異只有資料集與計數欄，故共用一支 DAG，並以：

- `indicator_id=marriage_count`
- `indicator_id=divorce_count`

區分兩種指標。

## 跨年度欄位陷阱

ODRP069不是固定欄位名：民國109–112與114實測為 `year`、`number_of_marry`；民國113改為 `statistic_yyy`、`marry_count`。ODRP071實測為 `statistic_yyy`、`divorce_count`。DAG先清理 BOM，再依角色別名正規化；必要欄位找不到會直接 `raise`，不會產出空資料。

## 年齡解析與18–35判定

來源年齡是5歲組，實測標籤為：

- `未滿15歲` → `(None, 14)`
- `15～19歲` → `(15, 19)`
- `20～24歲`、`25～29歲`、`30～34歲` 等 → 對應整數上下界
- `65歲以上` → `(65, None)`

任何不在解析規則內的標籤都會拋錯。18–35 判定為 **`apportioned`**：20–34歲的組別完整落在範圍內，但 `15–19` 需取18、19，`35–39` 需取35。DAG只保存來源原始組別，沒有假造單齡數字；下游應用同區、同年、同性別的單齡人口權重分攤。

## 低信心與方法限制

這裡被分攤的是結婚／離婚的事件（來源欄位是人數），不是人口本身。人口權重分攤隱含「事件率在同一5歲組內均勻」的假設，結婚與離婚年齡分布很可能不是均勻，因此18–35換算必須標示**低信心**；不可把它說成單齡實測值，也不可把事件數當人口數。來源是 `count`，不是 `rate`，沒有做比例縮放。

## 其他處理與對帳

- `gender` 取來源 `sex`，因為年齡與性別都是同一位結婚／離婚參與者；`marriage_type` 放在 `breakdown`，不跨主體混用。
- 行政區只輸出29個新北市行政區，代碼與既有青年 DAG 完全一致（板橋 `65000010` 起）。
- 所有參與分組與 breakdown 的維度先以 `未填` 補空，並明確使用 `dropna=False`，避免 pandas groupby 靜默丟掉 NaN key。
- 每個資料集／年度都做輸入列計數總和與聚合輸出總和對帳；不相等直接 `raise`。千分位逗號在數值解析時移除。

## 未解決事項

- 目前最新可用年度為民國114；DAG會往前後探測，未來有新年度即可自動納入。
- 來源沒有單一年齡，18–35無法達到死亡／出生資料的 `exact`；本支的 `apportioned` 結果應與人口權重及假設強度一起呈現。
- 尚未在本DAG內生成18–35的衍生列，避免在沒有可用權重時偷偷採用均勻分配。

## 表大小：90.5% 是零值，已改為只保留非零列

實測民國 114 年 `ODRP069`：

```
全國列數          618,240
新北市列數         48,720
新北市零值列       44,076  (90.5%)
新北市非零列        4,644  ( 9.5%)
```

原因是來源為**六維交叉表**：
`site_id × marriage_type × sex × nation × edu × age`
（行政區 × 婚姻類型 × 性別 × 國籍 × 教育程度 × 年齡）。
維度相乘後絕大多數組合在單一年度是沒有案例的。

本 DAG 原本輸出 **487,200 列**（10 個來源年度 × 48,720），
其中約 44 萬列的 `value = 0`。

### 已採行的處理

改為**只寫入非零列**，表大小從 48.7 萬降到約 4.1 萬列（縮小約 12 倍）。
`load_behavior` 是 `replace`，每次執行全量重寫近 50 萬列，
寫入時間與 Postgres 負擔都不必要。

改動前先確認過一件事：**對帳檢核比對的是「數值總和」而非列數**
（`input_total == output_total`）。數值總和才是真正該守住的不變量，
列數只是附帶。0 對總和沒有貢獻，所以濾零不影響對帳正確性——
實測濾零後每一年的 `input_total` 與 `output_total` 仍精確相等。
`reconciliations` 另外記下 `grouped_rows` 與 `dropped_zero_rows`，
讓「丟掉多少列」可追蹤，而不是靜默行為。

語意上這是安全的：下游查詢一律 `GROUP BY ... SUM(value)`，
缺列與零值列的結果完全相同。若某張圖需要顯式的零（例如熱區圖要畫出空白格），
應由查詢端 `LEFT JOIN` 維度表補零，而不是在事實表存 44 萬列的零。

### 實測結果

```
              修改前     修改後
每年輸出列數   48,720    2,977 - 5,003
全表列數      487,200      約 41,000
```

每一年的 `input_total` 與 `output_total` 完全不變
（例如 ODRP069 民國 114 年：36,498 = 36,498）。

同樣的處理也套用在 `youth_naturalized_population_age_ntpc` 與
`youth_indigenous_population_age_ntpc`，理由與作法一致。

# 新北市死亡人數（按死亡者單齡年齡）

## 來源驗證

```
https://www.ris.gov.tw/rs-opendata/api/v1/datastore/ODRP031/{民國年度}?PAGE={n}&COUNTY=新北市
```

- 平台：內政部戶政司 RIS OpenData，免驗證；官方 API 文件：
  `https://www.ris.gov.tw/rs-opendata/api/Main/docs/v1`
- 實測民國 113、114：不帶縣市參數皆為 HTTP 200、`responseCode=OD-0101-S`、各一頁；114加 `COUNTY=新北市` 回29個行政區。113加縣市參數反而回 `OD-0102-S`，改用無縣市參數後再由轉換層過濾，實際取得28個行政區，缺少板橋區；不補造零值。
- 從民國114向前探測至連續兩年查無資料（105、104），再向後探測（115、116皆查無資料），目前連續可用年度為民國106–114，即西元2017–2025。
- `COUNTY=新北市` 後 API 的 `totalDataSize` 仍可能顯示全國筆數；DAG只用成功碼、實際 `responseData` 與 `totalPage` 分頁，不用該欄位判斷新北筆數。
- 探勘時 `curl.exe -A` 已帶瀏覽器 User-Agent，但本機 Windows Schannel 回 `SEC_E_NO_CREDENTIALS`；這是本機 TLS 初始化問題，不是來源 HTTP 回應。DAG與 verify 改用 Python `urllib`，仍帶同一個瀏覽器 User-Agent。

轉換後共 **52,520 列**：民國106–112、114各29個行政區，民國113只有28個行政區；每個行政區輸出202列（0–99歲及100歲以上 × 男女）。

## 轉換與契約

來源是一列一行政區的寬表。每個 `0歲` 至 `99歲` 及 `100歲以上` 的男女欄位各轉成一列長表，輸出 `indicator_id=death_count_by_age`、`value_type=count`、`unit=人`；只輸出行政區層級，行政區代碼沿用既有青年 DAG（板橋 `65000010` 起）。

18–35 判定為 **`exact`**：死亡者年齡是單一年齡，18至35直接取用，沒有任何分攤或年齡推估。

## 已驗證的陷阱

### 一、RIS 查無資料不是 404

查無資料回 HTTP 200、`responseCode=OD-0102-S`（約64 bytes）；成功才是 `OD-0101-S`。DAG依回應碼判斷，不能用 HTTP 狀態碼判斷有無資料。

### 二、跨年度欄位名不同，且早期有 BOM

民國106–112與114主要使用 `statistic_yyy/site_id/death_age_000_m` 等英文欄位，民國113改用 `統計年度/區域別/0歲_男_人數` 等中文欄位；民國106、107的第一欄另帶 UTF-8 BOM。欄位先去 BOM，再依角色別名正規化；找不到必要角色或年齡欄位直接拋錯。

### 三、0歲的本年／去年出生是細分項，不是額外年齡

`0歲_男_人數`／`0歲_女_人數` 已包含 `本年出生`、`去年出生`。轉換只取0歲核心欄位，刻意排除這兩組細分欄；否則會重複計算。

### 四、總計欄不能和分齡列混加

`總計_計`、`總計_男`、`總計_女` 是行政區合計，只用來逐列驗證「男性分齡加總 = 男總計、女性分齡加總 = 女總計、男女合計 = 總計」。事實表不另寫總計列，避免下游把總計與分齡重複相加。每次執行都會檢查輸入總計等於輸出分齡總計，不符直接 `raise`。

## 性別主體

這份資料的年齡與性別都指死亡者本人，因此 `gender` 直接填 `male`／`female`，沒有把其他人的性別放入欄位。

## 未解決事項

- 目前 API 文件與實測年度上限為民國114；DAG會向後探測，未來新年度可在連續空年度規則內自動納入。
- `按照別` 實測為「按登記日期分」，因此 period 是年度登記口徑，不應在圖表標成死亡發生年度。

## ★ 民國 113 來源缺板橋區（2026-09-10 發現）

### 症狀

`youth_death_single_age_ntpc` 的民國 113（2024）全市死亡數是 **26,160**，
但 OAS 11842 戶籍動態同期是 **30,213**，差 4,053（-13.4%）。

其他年度兩個來源**完全一致**（2019-2023、2025 逐年相同）。
定義差異會每年產生一致偏移，不會只在某一年出現又消失——
所以這不是口徑問題，是其中一邊缺資料。

### 根因

**來源本身缺漏。** 戶政司 ODRP031 民國 113 期只回 28 個新北行政區，
**板橋區整筆不存在**：

```
ODRP031 113 + COUNTY=新北市   -> OD-0102-S 查無資料，0 列
ODRP031 113 不帶 COUNTY       -> 全國 367 列（112 期是 368 列）
   其中「區域別」含新北市者    -> 28 筆，無板橋區
```

28 個區加總正好是 26,160。板橋區是新北最大區（約 55 萬人），
一年死亡數約 4,000，與差額吻合。

**同期還有第二個陷阱**：民國 113 的欄位名是**中文**
（`統計年度`／`按照別`／`區域別`／`總計_計`），
其他年度是英文（`statistic_yyy`／`according`／`site_id`／`death_total`）。
本 DAG 原本就有中英對照表，所以資料抓得到；
但若用 `site_id` 直接取值會全部拿到 `None`、加總為 0。
（這是共用規則 B「同一個來源跨年度會改欄位名」的又一個實例。）

### 為什麼對帳沒抓到

**對帳比的是「解析後的輸入」對「輸出」，兩邊都建立在同一份殘缺來源上。**
`input_total=26160, output_total=26160` 完美相等，於是一路通過，
歷次全量掃描都是 PASS。

這和先前初任薪資「千元 vs 元」是同一種失效模式：
**自己跟自己對帳，永遠會過。** 唯一能抓到的是跨來源比對——
這次是靠新建的 OAS 11842 戶籍動態 DAG 才浮出來。

### 處置

**不修改來源數字，也不估算補回板橋區。** 改為：

1. 新增缺區守門：每個期別斷言 29 個行政區都在，
   缺漏且未登記在 `KNOWN_INCOMPLETE_YEARS` 就直接 `raise`。
2. 民國 113 登記在 `KNOWN_INCOMPLETE_YEARS`，附完整理由，執行時印出警告。
3. 該年度每一列的 `breakdown` 標 `source_incomplete: true`
   與 `missing_districts: ["板橋區"]`。
4. `reconciliations` 增加 `missing_districts` 欄位。

### 下游必須注意

**畫全市死亡趨勢時要排除民國 113，或明確標示為不完整。**
否則會呈現「2024 年死亡數驟降 13%、2025 年又跳回」的假訊號。
行政區層級的 28 個區數字是正確的，可以照用；只有板橋區 2024 缺值。

查詢時可用 `breakdown->>'source_incomplete' IS NULL` 濾掉不完整年度。
